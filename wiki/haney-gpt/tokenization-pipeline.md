# Haney GPT — Tokenization Pipeline

## Turning Text Into Numbers

Before a language model can process text, the text needs to become numbers. This is tokenization — the bridge between human language and machine learning. Haney Chat uses the GPT-2 tokenizer, which is a subword tokenizer based on Byte-Pair Encoding (BPE).

## Why Tokenization Matters

Tokenization shapes everything downstream. A poor tokenizer creates tokens that don't align with meaningful linguistic units. A good tokenizer balances vocabulary size (memory efficiency) with token meaningfulness (learning efficiency). The GPT-2 tokenizer, with its 50,257-token vocabulary, is a well-tested choice that handles English text efficiently.

## The Data Preparation Pipeline

Raw text goes through several stages before it reaches the model:

### Stage 1: Dataset Collection and Merging

The training corpus combines three datasets:

- **TinyStories** — Simple, short stories generated by GPT-3.5 and GPT-4. Great for teaching basic narrative structure and grammar.
- **Dolly-15k** — 15,000 human-generated instruction-following examples from Databricks. Teaches the model to respond to prompts and follow instructions.
- **UltraChat** — Large-scale conversational data. Teaches dialogue patterns, turn-taking, and natural conversation flow.

These datasets are merged into a unified format using the `merge_datasets.py` script. Each example gets wrapped with special tokens like `<|story|>` or `<|instruction|>` to help the model distinguish between different content types.

### Stage 2: Dataset Analysis

Before tokenizing, `analyze_dataset.py` examines the merged data — counting tokens, measuring sequence lengths, checking for anomalies. This step is often skipped in tutorials, but it's critical. You need to know:

- What's the average sequence length? (Determines your block_size choice)
- Are there outliers with extremely long sequences? (They'll need truncation)
- Is the data balanced across categories? (Imbalanced data leads to biased models)

### Stage 3: Tokenization

`tokenize_dataset.py` converts text into token IDs using the GPT-2 tokenizer. Each piece of text becomes a sequence of integers between 0 and 50,256. The tokenizer handles:

- Common words as single tokens ("the" → token 1037)
- Rare words split into subwords ("tokenization" → "token" + "ization")
- Punctuation as separate tokens
- Whitespace handling (GPT-2 uses a special scheme where spaces are part of the next token)

### Stage 4: Binary Encoding

The final step (`preparedata.py`) converts token sequences into a binary format for efficient training:

- Token IDs are stored as `uint16` (unsigned 16-bit integers) in numpy memmap files
- Training data goes to `train.bin`, validation data to `val.bin`
- The binary format allows random access without loading everything into RAM
- memmap files are memory-mapped — only accessed portions are loaded

## The Binary Format Advantage

Storing training data as binary memmap files is a crucial optimization. Text files would require parsing and tokenization on every training epoch. JSON would add overhead. The binary format means:

- Direct random access: jump to any position instantly
- Memory efficiency: only the accessed chunk is loaded into RAM
- Speed: reading raw bytes is faster than parsing text
- Compact: 517M tokens at 2 bytes each = about 1GB total

## Token Budget Considerations

With a vocabulary of 50,257 tokens, the model's output layer has 50,257 × 1280 ≈ 64 million parameters — just for predicting the next token. This is about 12% of the total model parameters. The vocabulary size directly affects both model size and the computational cost of the final projection.

Smaller vocabularies (like 32,000 used by some models) would reduce parameters but might not cover English text as efficiently — more words would need to be split into multiple subword tokens. The 50,257 vocabulary strikes a balance.

## Data Splits

The data is split into training and validation sets:

- **Train:** Used to update model weights. This is where learning happens.
- **Validation:** Held-out data used only for evaluation. The model never trains on this. Used to detect overfitting — if training loss decreases but validation loss increases, the model is memorizing rather than learning.

The split ensures we're measuring generalization, not memorization. A model that performs perfectly on training data but poorly on validation data is useless in practice.
